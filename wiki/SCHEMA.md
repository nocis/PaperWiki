# PaperWiki Schema

Conventions for the LLM-maintained knowledge base. Any agent session or compile run
that writes to `wiki/` MUST follow this document.

## Layers

| Layer | Location | Owner |
|-------|----------|-------|
| Raw sources (immutable) | `papers/compiled/` | human drops, compiler archives |
| Figures (derived) | `papers/compiled/<slug>_figures/` | PyMuPDF extractor (compile) |
| Inbox (work queue) | `papers/new/` | human drops PDFs; **compile empties it** |
| Wiki (knowledge) | `wiki/` | LLM writes; human reads |
| Derived index | `data/wiki-db.json` | regenerated by compile — never hand-edit |
| Reading notes | `comments/<slug>/` | human's private notes |
| Knowledge pieces | `knowledge/pieces/` | user's own knowledge, added via Add-to-knowledge |
| Knowledge articles | `knowledge/articles/` | derived by Knowledge Compile — never hand-edit |

## Invariants

1. **Comments quarantine.** Files under `comments/` are private reading notes.
   They are NEVER read by compile, NEVER included in any LLM prompt, and NEVER
   referenced from wiki pages. They are not knowledge.
2. **Inbox = incremental marker.** A PDF present in `papers/new/` is an
   unprocessed source. A successful compile moves every processed PDF to
   `papers/compiled/<slug>.pdf` (flat). On abort, unprocessed PDFs stay in the inbox.
3. **Canonical naming from the real title.** Dropped filenames are irrelevant —
   including arXiv ids like `2006.11239.pdf`. The compile slug is derived from
   the paper's REAL title (LLM-extracted → PDF metadata → filename fallback),
   and it names everything: `papers/compiled/<slug>.pdf`, `wiki/papers/<slug>.md`,
   `comments/<slug>/`, `/pdfs/<slug>.pdf`.
4. **Duplicates are non-fatal skips.** If a dropped file resolves to an
   already-compiled slug, it is moved to `papers/duplicates/` and the run
   continues. Only LLM/processing failures abort a run.
5. **Flat archive, stable URLs.** PDFs live flat in `papers/compiled/` and are
   served at `/pdfs/<slug>.pdf` by the app. Topic reorganizations never move PDFs.
6. **Wikilinks in body only.** Body text uses `[[slug]]` (resolved to app routes
   by the web renderer, by slug alone). YAML frontmatter uses bare slugs.
7. **Bidirectional linking.** source `milestone` ↔ topic Source Cluster;
   parent `children`/`subtopics` ↔ child `parent_milestone`;
   paper `cites` ↔ target paper `citedBy`. Compile verifies at every write.
8. **Max topic depth: 3.**
9. **Figures co-locate with the archive.** A paper's extracted figures live in
   `papers/compiled/<slug>_figures/` (named after the canonical slug) and are
   served at `/figures/<slug>/<file>`. The paper frontmatter lists them in
   `figures[]`, and the paper body embeds them under `## Figures` with absolute
   `/figures/...` URLs. Missing files or frontmatter/body mismatches are lint
   violations.
10. **Lint tiers.** Mechanical violations (reciprocal `cites`/`citedBy`,
    Feeds milestone sync, pruning broken figure references) are auto-fixed and
    logged; structural recommendations (split/promote/tag-to-parent) are queued
    in `wiki/proposals.md`, never auto-applied.

## Page formats

### Knowledge piece — `knowledge/pieces/<slug>.md`
Frontmatter: `slug, kind (note|chat), source (comment id for note, chat-<timestamp>
for chat), addedAt, updatedAt, tags[], topics[] (optional topic hints, nudges
grouping)`.
Body: the user's own text, verbatim at capture. Chat pieces may be edited
(PATCH edit-content); note pieces are immutable — delete + re-add. Topic hints
are managed separately via PATCH set-topics, allowed for both kinds. Edits
stamp `updatedAt` and make the knowledge layer stale (recompile refreshes
articles). Provenance: note pieces carry a `**Paper**: [[slug]] (p. N)` prefix
in the body (written at capture); chat pieces are labeled by `source`.

### Topic article — `knowledge/articles/<slug>.md` (DERIVED — regenerated every compile)
Frontmatter: `slug, title, compiledAt, pieceSlugs[], paperSlugs[],
relatedArticles[]`.
Sections: `## Definition`, `## Synthesis` (piece-linked claims, each cited as
`[[piece-slug]]`), `## Wiki Grounding` (evidence mapping per paper:
supported / contradicted / unaddressed), `## Academic Review` (novelty,
critique, limitations, research frontier — claims checked against wiki truth),
`## Related Articles`.

### Paper page — `wiki/papers/<slug>.md`
Frontmatter: `slug, title, authors[], venue, publishedAt (YYYY-MM), tags[]
(year/YYYY-MM + venue/<name>), milestone, subtopic|null, numPages, addedAt,
rawPath, pdfUrl, figures[], cites[], citedBy[]`.
Sections: `## Essence`, `## Contributions`, `## Figures` (markdown embeds of
`/figures/<slug>/<file>`, when figures exist), `## Critical Analysis`
(Novel Insight / Fundamental Limitations / Research Frontier),
`## Relations` (temporal context first), `## Citations` (the raw reference
list verbatim, numbered as extracted by the analyze LLM; entries resolved to
compiled papers get `→ [[slug]]`; header shows "N of M citations linked"),
`## Feeds`.

### Topic page — `wiki/topics/<slug>.md` (split-out children: `wiki/topics/<parent>/<child>.md`)
Frontmatter: `slug, name, definition, mode (standalone|merged|split),
parent_milestone|null, children[], subtopics[], tags[]`.
Sections: `## Definition`, `## Key Properties`, `## Source Cluster`,
inline `### <Subtopic>` sections (merged mode), `## Chronological Evolution`
(when >= 3 sources or chain change), `## Open Questions`.

### Topic modes & consolidation
- **standalone**: owns sources directly.
- **merged parent** (< 5 papers across subtopics): inline H3 subtopic sections.
- **split parent** (subtopic >= 5 papers): children get own files.
- Granularity: > 8 sources must split; 3–8 judgment; < 3 keep.
- Tag-to-parent: 3+ standalone topics sharing a tag → merged-parent candidate.
- All split/merge/promote operations are **Confirm-tier**: detected by compile,
  queued in `wiki/proposals.md`, never auto-applied.

### Classification fitness check
A source's core research question must genuinely fall within the topic's
milestone definition. Shared keywords do NOT imply shared research questions.
If the connection is indirect, create a new standalone topic — misclassification
is worse than a small new topic.

## Conventions

- Wiki language: `wiki_language` in `wiki/index.md` frontmatter (default `en`).
  Prose in that language; headings, YAML keys, slugs, wikilinks stay English.
- Slugs: kebab-case. Dates: ISO (`YYYY-MM-DD`, `YYYY-MM` for publications).
- Log entries: `## [YYYY-MM-DD] <operation> | <title>`.

## Operations

- **Compile** (`yarn compile`): incremental ingest — see `scripts/compile.ts`.
  Per paper: text extraction → LLM analysis → **figure extraction** (PyMuPDF
  via `scripts/figures.sh`, venv at `.pymupdf/`; best-effort, never aborts the
  run) → classification → synthesis → writes → move → derived index.
- **Lint** (`yarn lint:wiki`): wiki health inspection — see `scripts/lint.ts`.
  Auto-fixes mechanical invariant violations, queues structural proposals,
  reports broken wikilinks/figures. Web UI: `/health` (GET report, POST fixes).
- **Query** (`/chat`): retrieval over `index.md` → answer with `[[slug]]` citations.
  Answers are ephemeral; they are not written back to the wiki (v1).
- **Reorganize**: apply queued proposals (future: `yarn reorganize`).

## Knowledge layer

The `knowledge/` tree holds the human's own knowledge, separate from the
literature ground truth in `wiki/`. The wiki is written only by compile; the
knowledge tree is written only by Add-to-knowledge (pieces) and Knowledge
Compile (derived articles/index).

### Invariants

1. **Comments quarantine extends to knowledge.** The knowledge pipeline reads
   ONLY `knowledge/pieces/`. Notes become pieces exclusively via the explicit
   Add-to-knowledge UI action; the pipeline never reads `comments/`. A piece
   whose `source` doesn't match its kind (note → comment id, chat → `chat-`
   prefix) is unsanctioned and flagged by lint.
2. **From-zero compile.** Every Knowledge Compile re-reads all pieces + the
   latest wiki and regenerates ALL articles + index. No incremental state, no
   merging with hand edits.
3. **Articles are derived.** Hand-editing `knowledge/articles/` is useless —
   the next compile wipes it. Edits belong in pieces (delete + re-add).
4. **Overlapping membership.** A piece may appear in multiple articles
   (many-to-many). Articles may reference the same pieces; that is intended.
5. **Articles cite wiki truth, never restate it.** Article synthesis claims
   reference `[[paper-slug]]` (or `[[topic-slug]]`) for every claim about the
   literature; the Academic Review maps each piece claim to
   supported / contradicted / unaddressed by compiled papers.
6. **Piece hints.** `topics[]` in piece frontmatter nudges grouping; the LLM
   still decides the final article set.
7. **Knowledge compile requires LLM availability.** Same pre-flight and
   fail-hard rules as compile; progress tracked like compile.

### Knowledge compile flow

1. Read all pieces (`knowledge/pieces/*.md`).
2. Read latest wiki ground truth (index + topic/paper pages, bounded).
3. LLM call 1 — cluster: group pieces into overlapping topics (honoring
   `topics[]` hints); validate slugs code-side.
4. LLM call 2 per article — synthesize + academic review against wiki truth.
5. Write articles + `knowledge/index.md` + log entry. The UI derives its view
   live from the markdown — no separate db file.

Source of truth: `knowledge/pieces/`. Everything else under `knowledge/` is
derived and may be regenerated at any time.
